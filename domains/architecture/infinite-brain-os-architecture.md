# Infinite Brain OS — Architecture

**Source:** `sources/infinite-brain-os/`

## Overview

Infinite Brain OS is a git-backed operating system for running a business with AI agents. It uses plain Markdown and YAML files organized into a typed entity graph — commands, agents, skills, rules, workflows, tools, knowledge namespaces, data pointers, memory nodes, projects, and departments — that any file-reading AI agent can navigate, read, and write. No database, no server, no vendor lock-in. The system ships with a complete fictional worked example (Emberline Studio) demonstrating all entity types through cross-linked files.

## Architecture

The architecture follows a **flat git-repository structure** with typed subdirectories, governed by a contract layer (`_system/`) that validates all frontmatter, wikilinks, and lifecycle states.

```
infinite-brain-os/
├── _system/              ← The operative contract
│   ├── validate.sh       ← Frontmatter + wikilink validation
│   ├── namespaces/       ← Namespace registration
│   ├── *-rules.md        ← 40+ rule files (promotion, session, deprecation, etc.)
│   └── surface-registry/ ← Retrieval surface metadata
├── knowledge/            ← Namespace-first knowledge graph
│   ├── ai-architecture/  ← Reference architecture (read-first doctrine)
│   ├── [namespace]/      ← Each with INDEX.md, canon/, playbooks/, support/, synthesis/
│   └── _examples/        ← 8 unregistered profile scaffolds
├── entities/             ← Canonical executable entities
│   ├── commands/         ← Reusable agent commands
│   ├── agents/           ← Agent definitions with tool assignments
│   ├── skills/           ← Skill definitions
│   └── rules/            ← Business rules and constraints
├── .claude/ .codex/      ← Runtime adapter shims (autogenerated, never edited directly)
├── workflows/            ← Agentic reasoning pipelines (Markdown)
├── sessions/             ← Full audit trail of AI work sessions
├── departments/          ← Assemblies over entities (one folder per operating lane)
├── projects/             ← One PLAN.md per project with tasks
├── intake/               ← Inbound flow: source captures, routing, processed receipts
├── data/                 ← Pointers to live data (never the numbers themselves)
├── memory/               ← Reviewed learnings from past sessions
├── outputs/              ← Produced artifacts with lineage metadata
└── tools/                ← Pointer nodes over bounded capabilities
```

### Namespace Knowledge Architecture

Knowledge is organized into namespaces (`knowledge/<namespace>/`), each with a standard base structure: `INDEX.md` (entry point), `canon/` (operator-approved truth), `playbooks/` (procedures), `support/` (provenance), and `synthesis/` (derived thinking). Eight namespace profiles provide templates for doctrine, data-systems, design-systems, content-strategy, tool-contracts, and more.

### Entity Lifecycle

Every typed entity progresses through four lifecycle states enforced by frontmatter: `scratch` (new, unvalidated) → `research` (validated, worth refining) → `candidate` (nominated for promotion) → `canon` (operator-approved). Promotion requires explicit operator review — agents cannot self-promote.

### Dual-Adapter Architecture

Executable entities (commands, agents, skills, rules) live canonically in `entities/` and are loaded through runtime adapter shims (`.claude/`, `.codex/`). Editing the canonical file then running `bash sync-adapters.sh` keeps shims in sync — agents never edit shims directly.

## Key Components

| Component | Location | Role |
|-----------|----------|------|
| **Contract layer** | `_system/` | 40+ rule files, schema definitions, registry files |
| **Validation script** | `_system/validate.sh` | Enforces frontmatter integrity, wikilink resolution, lifecycle rules |
| **Canonical entities** | `entities/` | Commands, agents, skills, rules in typed YAML frontmatter |
| **Adapter shims** | `.claude/`, `.codex/` | Runtime symlinks synced from canonical entities |
| **Session audit** | `sessions/` | Active/closed sessions with transcript logs, running notes, closeout reviews |
| **Namespace knowledge** | `knowledge/<ns>/` | Per-namespace knowledge with canon/playbooks/support/synthesis |
| **Worked example** | `knowledge/emberline-studio/` | Complete fictional candle business demonstrating all entity types |

### Frontmatter Contract

Every node-bearing file requires YAML frontmatter with minimum fields: `id` (kebab-case), `type` (one of 11 entity types), `namespace`, `lifecycle_state`. Serious nodes add `summary`, `confidence`, `retrieval_class`, `export_class`, `edges`, and `created` for richer graph traversal.
